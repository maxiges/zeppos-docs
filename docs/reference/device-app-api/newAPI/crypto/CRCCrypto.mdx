# Cyclic Redundancy Check (CRC) Checksums

The Cyclic Redundancy Check (CRC) component in the `@zos/crypto` module provides ultra-fast, hardware-efficient tools designed exclusively for detecting accidental data mutations or storage errors.

### 💡 Architectural Note: Checksums vs. Asymmetric Signatures (ECDSA)

It is crucial for developers to distinguish between non-cryptographic error-detection mechanisms like **CRC** and cryptographic signature schemas like **ECDSA**:

- **CRC (Cyclic Redundancy Checks):** Optimized purely for raw computation execution speeds and exceptionally low battery consumption. It is highly effective at catching random hardware bit flips, storage degradation, or packet drops over weak BLE/Wi-Fi channels. However, it offers **no defense against malicious attacks**. Because the math behind CRC is completely linear, an attacker can intentionally modify a payload and generate a matching valid CRC value instantly.
- **ECDSA (Elliptic Curve Digital Signature Algorithm):** Utilizes asymmetric private/public key pairs to guarantee non-repudiation, strict data authenticity, and proof of origin. It actively protects against malicious tampering since a valid signature cannot be forged without the private key, even if the payload data is visible.

> **Byte Ordering Hint:** All verification outputs generated by the CRC engine are natively processed, written, and returned in standard **Little-Endian** byte configurations.

---

### Endianness & Byte Alignment

Both `alg.CRC16` and `alg.CRC32` variants emit execution outputs formatted in **Little-Endian byte order** (least significant byte stored at the lowest memory address). When transmitting these checksums across network boundaries to Big-Endian systems or parsing them in low-level drivers, explicit byte-swapping operations may be structurally required.

## API Reference & Type Schemas

### `createCrypto()`

Instantiates a reusable, stateful cryptographic context designed to process inputs utilizing the selected CRC algorithm variant.

#### Method Signature

```ts
function createCrypto(algorithmId: typeof alg.CRC16 | typeof alg.CRC32): CRCCrypto | undefined
```

#### Algorithm Registry (`algorithmId`)

| Option Identifier | Hardware/Software Mode             | Supported API Level | Technical Description & Error Detection Capability                                                                                                      |
| :---------------- | :--------------------------------- | :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `alg.CRC16`       | Optimized Lookup / Hardware Engine | `3.0`               | Computes a 16-bit (2-byte) mathematical checksum. Ideal for compact structures, Bluetooth Low Energy packet payloads, and small memory state fragments. |
| `alg.CRC32`       | Optimized Lookup / Hardware Engine | `3.0`               | Computes a 32-bit (4-byte) mathematical checksum. Essential for high-reliability applications, OTA update packages, and flash filesystem blocks.        |

#### Return Value

- Returns a `CRCCrypto` instance configured to execute calculations for the specified algorithm payload.
- Returns `undefined` if system resource allocation failures occur, or if an unsupported `algorithmId` is supplied.

---

### `CRCCrypto`

An operational instance interface exposed following successful context creation via `createCrypto()`. This instance exposes an immutable, execute-only pipeline via the `encrypt()` routine.

### Methods

#### `encrypt()`

Computes the final checksum value by processing the targeted contiguous binary payload.

#### Method Signature

```ts
encrypt(data: createCrypto.CRCData): CRCResult | undefined
```

#### Parameters (`CRCData`)

| Parameter Name | Data Type                                   | Required | Default | Technical Description & Boundaries                                                                                                                                                                                                                                                                                                                    |
| :------------- | :------------------------------------------ | :------- | :------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data`         | `number[]` \| `ArrayBuffer` \| `Uint8Array` | **Yes**  | _None_  | The target binary payload container targeted for immediate execution. Arrays of numbers are parsed as structural byte arrays where integers must be bounded inside the `[0, 255]` range; values exceeding this boundary undergo implicit bitmask wrapping (`& 0xFF`). Passing enormous buffers without slicing can trigger localized heap exhaustion. |

#### Return Value Schema (`CRCResult`)

| Property Name | Data Type     | Structural Definition & System Architecture Scope                                                                                                                         |
| :------------ | :------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `data`        | `ArrayBuffer` | A raw, fixed-length allocation pool containing the computed mathematical remainder formatted strictly in **Little-Endian** layout (2 bytes for CRC16; 4 bytes for CRC32). |
| `length`      | `number`      | Reflects the strict memory size boundary of the generated `ArrayBuffer` output expressed in raw bytes.                                                                    |

The following implementation initializes a `CRC16` computational context, maps a small raw array of integers representing raw sensor configurations, and derives a 2-byte, Little-Endian checksum value.

```js
import { alg, createCrypto } from '@zos/crypto'

// Instantiate the stateful CRC16 computational engine context
const crc16 = createCrypto(alg.CRC16)
if (!crc16) {
  throw new Error('OS Runtime Exception: Failed to initialize hardware-accelerated CRC16 context.')
}

// Low-level byte payload representing hardware configuration adjustments
const sensorConfigPayload = [0x01, 0x02, 0x03]

// Calculate the error-detection code via the encrypt pipeline
const executionResult = crc16.encrypt(sensorConfigPayload)

if (executionResult) {
  // Expected internal length for CRC16 is exactly 2 bytes
  console.log(`CRC16 Execution Success. Output Byte Length: ${executionResult.length}`)

  // Wrap raw ArrayBuffer view to log the Little-Endian output structure
  const view = new Uint8Array(executionResult.data)
  console.log(
    `Hexadecimal Byte Representation: [${Array.from(view)
      .map((b) => '0x' + b.toString(16).padStart(2, '0'))
      .join(', ')}]`
  )
} else {
  console.log('Error: Computation pipeline faulted. Verify system heap allocation.')
}
```

This implementation leverages a standardized typed array container (`Uint8Array`) to perform a 32-bit checksum across raw, fixed-size hardware memory segments.

```js
import { alg, createCrypto } from '@zos/crypto'

// Allocate the 32-bit engine context optimized for heavy-burst error coverage
const crc32 = createCrypto(alg.CRC32)
if (!crc32) {
  throw new Error('OS Runtime Exception: Failed to initialize hardware-accelerated CRC32 context.')
}

// Allocate an explicit typed memory space representing a small serialization buffer
const telemetryFrame = new Uint8Array([0x0a, 0x1f, 0x2b, 0x3c])

// Execute the mathematical polynomial division matrix
const result = crc32.encrypt(telemetryFrame)

if (result) {
  // Expected internal length for CRC32 is exactly 4 bytes
  console.log(`CRC32 Processing Finalized. Checksum Byte Length: ${result.length}`)

  // Instantiating a DataView simplifies raw interpretation across endian boundaries
  const view = new DataView(result.data)
  // Retrieve the 32-bit unsigned integer using true littleEndian flag set to true
  const computedUint32 = view.getUint32(0, true)
  console.log(
    `Computed Checksum Unsigned Integer: ${computedUint32} (0x${computedUint32.toString(16).toUpperCase()})`
  )
}
```

Real-world implementation demonstrating a complete end-to-end data integrity validation flow. This simulates calculating a CRC32 checksum prior to inter-process communication or wireless Bluetooth transmission, and validating it against a recalculated variant upon packet receipt.

```js
import { alg, createCrypto } from '@zos/crypto'

/**
 * Simulates the localized encoding and transmission phase
 */
// The target raw text payload container converted to ASCII byte sequences ("Hello")
const originalBinaryPayload = new Uint8Array([0x48, 0x65, 0x6c, 0x6c, 0x6f])

// Sender generates a tracking hash context for validation
const senderContext = createCrypto(alg.CRC32)
if (!senderContext) throw new Error('Sender Context Initialization Failure')

const expectedToken = senderContext.encrypt(originalBinaryPayload)
if (!expectedToken) throw new Error('Failed to generate baseline validation checksum')

// Extract raw byte copies out of the initial buffer configuration
const senderChecksumBytes = new Uint8Array(expectedToken.data)

// --- SIMULATED HARDWARE BUS TRANSMISSION HAPPNING HERE ---

/**
 * Simulates the receiving subsystem or localized storage reading stage
 */
// Received data sequence from the hardware layer
const receivedBinaryPayload = new Uint8Array([0x48, 0x65, 0x6c, 0x6c, 0x6f])

const receiverContext = createCrypto(alg.CRC32)
if (!receiverContext) throw new Error('Receiver Context Initialization Failure')

const actualToken = receiverContext.encrypt(receivedBinaryPayload)

if (actualToken) {
  const receiverChecksumBytes = new Uint8Array(actualToken.data)

  // Enforce rigid array length and multi-byte alignment evaluations
  let isPayloadIntact = senderChecksumBytes.length === receiverChecksumBytes.length

  if (isPayloadIntact) {
    // Perform linear execution pass across the byte arrays
    for (let i = 0; i < senderChecksumBytes.length; i++) {
      if (senderChecksumBytes[i] !== receiverChecksumBytes[i]) {
        isPayloadIntact = false // Mismatch detected; channel injection or corruption occurred
        break
      }
    }
  }

  if (isPayloadIntact) {
    console.log('Data integrity verified successfully ✓. No transient channel errors detected.')
  } else {
    console.log('CRITICAL ERROR: Data corruption or bit-flip detected during transmission ✗.')
  }
}
```
